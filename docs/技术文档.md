# Tugline 技术文档

> 多仓库 GitHub 一键化部署平台（Java 实现）· v0.1 设计与实现说明

---

## 1. 项目定位

Tugline 解决"一个人维护多个 GitHub 项目时，每次发版都要挨个 pull、build、restart、部署、验证"的重复劳动。

v0.1 目标：**面向 Java 项目（Maven / Gradle），提供从 GitHub 仓库到可访问服务的一键化部署平台**：

```
GitHub Repos（多仓库）
   │ pull（Webhook 自动触发 / 控制台手动触发）
   ▼
Build Stage（自动探测 pom.xml / build.gradle → mvn package / gradle build）
   │ ship
   ▼
Deploy Stage（停旧进程 → java -jar 启动新进程 → 指定端口）
   │ live
   ▼
Preview（http://localhost:{port} 在线演示地址 + 健康检查）
```

不绑定云厂商、不强制容器化：本地机器、云服务器都可作为部署目标（部署目标 = Tugline 所在机器）。

## 2. 技术选型（Java 栈）

| 层级 | 选型 | 版本 | 理由 |
|---|---|---|---|
| 语言 | Java | 21+（LTS，兼容 24 运行时） | 用户主语言 |
| 服务框架 | Spring Boot（starter-web） | 3.5.x | 生态成熟、内嵌 Tomcat、零额外部署 |
| 存储 | JSON 文件（`data/state.json`，原子写入） | — | v0.1 单机无需数据库，零依赖；后续可平滑换 SQLite/H2 |
| Git 操作 | `ProcessBuilder` 调用系统 `git` | git ≥ 2.30 | 复用本机凭据/代理配置，避免引入 JGit 的凭据复杂度 |
| 构建调用 | `ProcessBuilder` 调用 `mvn` / `mvnw` / `gradlew` / `javac` | — | 与开发者本机构建行为一致，日志即真实构建日志 |
| 进程管理 | `Process` + `ProcessHandle` + 进程组信号 | JDK 内置 | 平台无关地启停 Java 应用进程 |
| Webhook 校验 | `javax.crypto.Mac` HMAC-SHA256 | JDK 内置 | GitHub `X-Hub-Signature-256` 标准校验 |
| 前端 | 原生 HTML/JS/CSS（Spring Boot 静态资源） | — | 无构建链、无 node_modules，轮询刷新足够 |
| 日志 | 直接落盘文本文件 + 接口 tail 读取 | — | 构建日志可追溯、可重放（README 要求） |

**依赖清单极简：仅 `spring-boot-starter-web` 一个依赖**，其余全部走 JDK / 系统命令。

## 4. 模块设计

### 4.1 包结构

```
src/main/java/dev/tugline/
├── TuglineApplication.java        # 启动类
├── config/
│   └── TuglineProperties.java     # dataDir / 服务端口 / 端口池 / 超时配置
├── model/
│   ├── Repo.java                   # 仓库定义
│   ├── Run.java                    # 一次流水线执行
│   ├── RunStep.java                # 步骤（fetch/build/deploy/health）
│   └── RuntimeState.java           # 受管应用进程状态
├── store/
│   └── JsonStore.java              # state.json 加载/保存（原子写 + 读写锁）
├── core/
│   ├── GitService.java             # clone / pull / 当前 commit
│   ├── BuildService.java           # 构建体系探测 + 执行 + 产物定位
│   ├── AppRuntimeService.java      # java 进程启停 / 健康检查 / 日志
│   └── PipelineService.java        # 流水线编排（状态机 + 互斥）
└── web/
    ├── RepoController.java         # 仓库 CRUD + 触发操作
    ├── RunController.java          # 运行记录 + 日志读取
    ├── WebhookController.java      # GitHub Webhook 接收
    └── ApiExceptionHandler.java    # 统一错误返回
```

### 4.2 各模块职责

| 模块 | 职责 | 关键实现点 |
|---|---|---|
| **JsonStore** | 仓库/运行记录/运行时状态持久化 | 临时文件写入 + `Files.move` 原子替换；`ReentrantReadWriteLock` 保护；运行记录环形保留最近 50 条 |
| **GitService** | 首次 `clone --branch --single-branch --depth 50`；后续 `fetch + reset --hard origin/{branch}` | 私有仓库支持把 token 注入 remote URL；返回当前 commit SHA |
| **BuildService** | 探测构建体系并执行构建；定位产物 | 优先级：`mvnw` → `mvn`（存在 pom.xml）；`gradlew` → `gradle`（存在 build.gradle[.kts]）；两者皆无且存在 .java 源码 → `javac` 兜底。产物查找：`target/*.jar`、`build/libs/*.jar`（排除 sources/javadoc/original-），取最新；javac 场景扫描 `public static void main` 定位主类 |
| **AppRuntimeService** | 受管 java 进程的启停、日志、健康检查 | `ProcessBuilder.redirectErrorStream` 合并日志落盘 `data/logs/app-{repoId}.log`；`detached` 进程组，停止时 SIGTERM → 3s 后 SIGKILL；健康检查按 `healthPath → /actuator/health → /health → /healthz → /` 顺序轮询，任意 HTTP 响应即视为端口存活，90s 超时 |
| **PipelineService** | 四步流水线编排 + 同仓库互斥 | 单线程池执行保证步骤串行；`ConcurrentHashMap<repoId, runId>` 防并发重复触发；每步状态实时写回 store，前端轮询可见 |

### 4.3 流水线状态机

```
run.status: RUNNING ──┬──► SUCCESS
                      └──► FAILED

step:  FETCH ──► BUILD ──► DEPLOY ──► HEALTH
       拉取代码    构建       部署        健康检查

每步: PENDING → RUNNING → SUCCESS | FAILED
```

- **FETCH**：clone 或 pull，记录 commit SHA；失败即终止。
- **BUILD**：探测并执行构建；失败即终止（保留上一次已部署版本继续运行）。
- **DEPLOY**：先停旧进程 → 以新产物启动。Spring Boot 项目自动追加 `--server.port={port}`，同时注入环境变量 `PORT`。
- **HEALTH**：轮询健康端点。**失败不自动回滚**（保留进程便于排障），在 v0.3 引入灰度/回滚（与 README Roadmap 对齐）。

## 5. 数据模型

```jsonc
// data/state.json
{
  "repos": [{
    "id": "r_a1b2c3",              // r_ + 随机
    "name": "demo-service",        // 取 URL 尾段去 .git
    "url": "https://github.com/org/demo-service.git",
    "branch": "main",
    "token": "",                   // 私有仓库可选
    "secret": "",                  // Webhook 密钥（HMAC 校验）
    "port": 9001,                  // 0 = 自动分配（9001 起递增）
    "healthPath": "",              // 空 = 自动探测
    "autoDeploy": true,            // push 事件是否自动部署
    "createdAt": 1730000000000
  }],
  "runs": [{                        // 最近 50 条
    "id": "run_x9y8z7",
    "repoId": "r_a1b2c3",
    "trigger": "MANUAL | WEBHOOK",
    "branch": "main",
    "commit": "abc1234",
    "status": "RUNNING | SUCCESS | FAILED",
    "steps": [{
      "key": "BUILD", "name": "构建",
      "status": "SUCCESS",
      "startAt": 0, "endAt": 0
    }],
    "artifact": "target/demo-1.0.jar",
    "error": "",
    "createdAt": 0, "endAt": 0
  }],
  "runtime": {                      // repoId → 进程状态
    "r_a1b2c3": {
      "pid": 12345, "port": 9001,
      "artifact": "target/demo-1.0.jar",
      "mainClass": null,            // javac 兜底时才有
      "startedAt": 0,
      "health": "UP | DOWN | STARTING",
      "commit": "abc1234"
    }
  }
}
```

**磁盘布局**：

```
data/
├── state.json
├── repos/{repoId}/          # git 工作副本
├── build/{repoId}/          # javac 兜底的编译输出
└── logs/
    ├── run-{runId}-{step}.log   # 每步构建/部署日志
    └── app-{repoId}.log         # 应用运行日志（stdout/stderr）
```

## 6. REST API 设计

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/repos` | 仓库列表（含运行时状态、最近一次 run 概要） |
| POST | `/api/repos` | 添加仓库（`git ls-remote` 预校验连通性与分支） |
| DELETE | `/api/repos/{id}` | 停止应用并移除仓库数据 |
| POST | `/api/repos/{id}/deploy` | 触发完整流水线（pull→build→deploy→health） |
| POST | `/api/repos/{id}/stop` | 停止受管应用进程 |
| POST | `/api/repos/{id}/restart` | 用现有产物重启（不重新构建） |
| GET | `/api/repos/{id}/runs` | 该仓库运行历史 |
| GET | `/api/repos/{id}/applog?tail=300` | 应用运行日志 |
| GET | `/api/runs/{id}` | run 详情（步骤状态） |
| GET | `/api/runs/{id}/logs?step=BUILD&tail=300` | 某一步的日志 |
| POST | `/api/webhook/{repoId}` | GitHub Webhook 入口 |

**Webhook 约定**：

- URL：`http://{host}:7070/api/webhook/{repoId}`
- 仅处理 `push` 事件且 `ref == refs/heads/{branch}`
- 若仓库配置了 `secret`，强校验 `X-Hub-Signature-256: sha256=HMAC_SHA256(secret, rawBody)`（`MessageDigest.isEqual` 恒时比较）；`ping` 事件直接返回 200 供 GitHub 首次验证
- `autoDeploy=false` 时 push 只记录不触发

## 7. 关键流程时序

### 7.1 一键部署（手动）

```
控制台 ──POST /deploy──► PipelineService
                          │ 同仓库已有 run？→ 409 拒绝
                          ▼
              [FETCH] git clone/pull ──失败──► run=FAILED
                          │ commit SHA
                          ▼
              [BUILD] 探测 mvn/gradle/javac → package ──失败──► FAILED（旧版本继续在线）
                          │ 定位 jar
                          ▼
              [DEPLOY] 停旧进程(PID) → java -jar --server.port=9001
                          ▼
              [HEALTH] 2s 间隔轮询 90s ──超时──► FAILED（进程保留）
                          │ 200 OK
                          ▼
                     run=SUCCESS，演示地址 http://localhost:9001 可用
```

### 7.2 Webhook 自动部署

```
GitHub push ──► POST /api/webhook/{repoId}
                  │ HMAC-SHA256 校验（配置了 secret 时）
                  │ ref 过滤 + autoDeploy 判断
                  ▼
             异步触发同 7.1 流水线，立即返回 202
```

## 8. 配置

`application.yml`：

```yaml
server:
  port: 7070            # Tugline 控制台端口
tugline:
  data-dir: ./data      # 状态 / 仓库副本 / 日志
  port-base: 9001       # 应用端口自动分配起始值
  build-timeout-min: 15
  health-timeout-sec: 90
```

环境要求：JDK 21+、git、Maven（或项目自带 mvnw）/ Gradle（或项目自带 gradlew）。

## 8.5 应用自报访问信息（.tugline.yml 约定）

应用的入口页面不一定在根路径（如 Citadel 的管理页在 `/admin/index.html`）。应用可在**仓库根目录**放置 `.tugline.yml` 声明访问信息，Tugline 在 FETCH 步骤后自动读取采用（仓库手动配置过的字段优先，不会被覆盖）：

```yaml
tugline:
  preview-path: /admin/index.html   # 演示地址的访问路径（默认 /）
  health-path: /actuator/health     # 健康检查路径（留空走自动探测链）
  display-name: Citadel 权限中心     # 可选，控制台展示名
```

- 解析失败或文件不存在 → 静默忽略，不影响部署
- 控制台「访问路径」一栏点击可手动修改（`POST /api/repos/{id}/update`）
- 生效后「在线演示地址」卡片显示完整可访问 URL（端口 + 路径）

## 9. 快速开始

```bash
# 1. 打包
mvn -DskipTests package

# 2. 启动
java -jar target/tugline-0.1.0.jar
# 或开发模式：mvn spring-boot:run

# 3. 打开控制台
open http://localhost:7070

# 4. 添加仓库 → 点击「一键部署」
# 5. GitHub 仓库 → Settings → Webhooks → 填入控制台显示的 Webhook URL 与密钥
```

## 10. 与 README Roadmap 的对应关系

| Roadmap | 本实现 |

| v0.1 单仓库 pull + build + 本地部署、构建日志与 Dashboard | ✅ 本文档范围 |
